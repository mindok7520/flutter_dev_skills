## 주요 결정

1. 자료 저장소와 대상 앱을 구분한다. 기존 앱의 매니페스트·README·라이선스·SDK·코드를 자동 변경하지 않는다.
2. 공통 정책은 docs에 두고 도구별 설정은 참조한다. 필요한 프롬프트·스킬만 읽어 문맥 사용량을 줄인다.
3. Flutter 예시 버전은 템플릿에만 둔다. 대상 프로젝트의 현재 도구 체인을 먼저 확인한다.
4. 출시·성능 도구는 실제 증거가 없으면 통과를 주장하지 않는다. 미설정 출시 검증은 의도적으로 실패한다.
5. 원문 정규식 대신 YAML 구조와 CommonMark 파서로 워크플로·문서 링크를 검사한다.

## 검증 증거

| 검증 | 환경·방법 | 결과 |
| --- | --- | --- |
| 자료 구조·링크·인코딩·메타데이터 | Python 3.13, `python scripts/validate.py` | 통과 |
| 설치·정책 회귀 테스트 | `python -m unittest discover -s tests -v` | 14개 통과 |
| 자료 도구 의존성 | `python scripts/audit_dependencies.py` | 확인 시 OSV가 알려진 취약점 결과를 반환하지 않음 |
| 스킬 형식 | 공식 skill-creator의 quick_validate.py | 24개 통과 |
| 스킬 적용 | 대화 이력 없는 별도 에이전트의 세션 복원·코드 리뷰 | 자료/앱 구분 확인, 재현된 검사 결함 수정 |
| 도입 흐름 | 저장소 밖의 시험 Flutter 프로젝트에 미리보기·실제 복사 | 기존 pubspec·앱 코드·gitignore·README 해시 유지 |
| Dart 도구 | 별도 시험 패키지의 정적 분석 | 문제 없음 |
| 앱 개발 도구 경로 | 시험 프로젝트에서 bootstrap·check·의존성 점검·웹 후보 확인 | 정상 경로 확인 |
| 성능·출시 실패 처리 | 합성 입력과 미설정 프로젝트 | 예산 초과·단위 불일치·표본 부족·출시 미승인·debug 서명·테스트 부재 거부 |

합성 입력은 검증 도구의 동작을 시험하기 위한 것이며 앱의 실제 성능 측정값이 아니다. 이 검증은 상용 출시·실기기·스토어 심사·실제 배포를 포함하지 않는다.

## 원격 게시와 복구

빈 저장소의 최초 초기화 예외에 따라 이슈 브랜치에서 기준 커밋을 만든다. `master`와 `develop`은 같은 커밋을 가리키도록 초기화하며, 이후 작업은 PR 흐름을 따른다. 원격 게시 결과와 정확한 커밋은 이슈 #1에 기록한다. 게시 기록이 없다면 푸시 완료를 추측하지 않는다.
