# Product design brief template

Copy the sections below into a product-specific design record or fill this document in the target app. Collect answers through [the design workflow](DESIGN_WORKFLOW.md). Keep unresolved items explicitly undecided, with an owner or next question; this template is not an approved product direction.

## Product and audience

Describe the product's main value, primary users, usage context, and the most important task. Link the product's `PROJECT.md`. Identify needs such as outdoor use, one-handed operation, assistive technology, intermittent connectivity, or dense professional workflows only when relevant.

## Scope and constraints

Record target platforms, supported input methods, initial languages, representative window sizes, time/budget constraints, existing implementation, and features excluded from this design. Distinguish a visual redesign from a change to navigation or business behavior.

## Visual direction

Record three to five descriptive qualities and explain how each changes a design decision. For example, "calm" might mean restrained motion and fewer competing emphasis levels; it is not automatically a beige palette. Define information density, tone of copy, imagery, and the intended relationship to platform conventions.

## Reference analysis

For each reference, record its URL or local image path, the exact screen/state, what the user likes, what to avoid, and how it fits the product. Distinguish observed details from inference. Record rights and provenance for assets that will actually be used; a reference screenshot is not automatically a licensed production asset.

## Content and key flow

List the first representative screen and its primary task, realistic sample content, navigation entry/exit, and the key success state. Include likely extremes such as an empty history, long names, many records, a denied permission, and a recoverable error.

## Shared visual rules

Link chosen color/text/spacing/motion roles, reusable components, and platform adaptations. Record the reason for each distinctive element. Keep unchosen packages and effects as options rather than installed dependencies.

## Acceptance and evidence

Record the agreed visual and functional criteria, test environments, screenshot locations, keyboard/screen-reader checks, and performance budgets relevant to this scope. Define how the user will recognize success without relying on a subjective numeric beauty score.

## Decisions and approval

Record the actual user answer or delegated decision, its date or conversation reference, approved scope, remaining questions, and the next task. Use the status `Draft`, `Awaiting user decision`, or `Approved scope recorded` only when supported by evidence. An AI recommendation alone cannot set the last status.
